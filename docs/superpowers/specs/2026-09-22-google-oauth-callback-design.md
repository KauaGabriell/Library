# Google OAuth Callback Design

## Scope

Implement the second half of the Google OAuth Authorization Code + PKCE flow. The callback validates and consumes the temporary authorization, exchanges the Google code, resolves the Google identity, creates or links local data, creates a local session, sets the existing session cookie, and redirects to the configured frontend.

Rate limiting and frontend UI are outside this scope.

## HTTP contract

Endpoint: `GET /auth/google/callback`

Required query parameters:

- `code`: short-lived authorization code returned by Google.
- `state`: opaque value originally generated by the API.

Zod validates both values as non-empty strings. Invalid query input follows the global `400 VALIDATION_ERROR` contract.

Successful completion sets the existing `session` cookie and redirects with `302` to `FRONTEND_URL`. The callback never returns Google tokens to the browser.

## Components

### Route

The Fastify route validates `code` and `state`, calls the auth service, sets the session cookie using the existing helper, and redirects to the frontend. It contains no Prisma queries or Google-specific protocol logic.

### Auth service

The service coordinates the callback:

1. Hash the received `state` using the same algorithm and encoding used during authorization creation.
2. Atomically consume the matching temporary authorization.
3. Exchange `code` and the stored `codeVerifier` for a Google access token.
4. Fetch and validate the Google profile.
5. Reject profiles whose email is not verified.
6. In one database transaction, resolve the local identity and create a local session.
7. Return only the local session token, expiration, and public user required by the route.

### Repository

The repository provides focused persistence operations:

- Atomically consume an OAuth authorization.
- Find an OAuth account by provider and provider account ID.
- Create an OAuth account linked to a user.
- Find a user by normalized email.
- Create an OAuth-only user with no password hash.
- Create a local session.

The repository receives either the Prisma client or a transaction client as appropriate.

### Google adapter

The existing adapter remains responsible for external Google HTTP calls:

- Exchange authorization code using the stored PKCE verifier.
- Fetch the Google profile.
- Map timeouts, invalid payloads, network failures, and non-success responses to `502 INTEGRATION_ERROR`.

## Atomic state consumption

Use `updateManyAndReturn` with all validity conditions in the same database operation:

- `provider = GOOGLE`
- `stateHash` matches
- `consumedAt = null`
- `expiresAt > now`

The update sets `consumedAt` to the current time. Exactly one returned record means the state was valid and is now consumed. Zero records means the state is invalid, expired, or already used and results in `401 UNAUTHENTICATED`.

This operation prevents two simultaneous callbacks from consuming the same authorization. The record remains stored for audit and diagnosis.

## Identity resolution

After receiving a verified Google profile:

1. Search `OAuthAccount` by the compound identity `(GOOGLE, providerAccountId)`.
2. If found, use its associated user.
3. Otherwise normalize the Google email and search for an existing local user.
4. If a user exists, link a new Google OAuth account to that user.
5. If no user exists, create a user without `passwordHash`, then create its Google OAuth account.

OAuth account linking, optional user creation, and local session creation occur in one Prisma transaction. A failure leaves no partial identity data.

The database compound unique constraint on `(provider, providerAccountId)` remains the final concurrency guard.

## Error handling

- Missing or malformed query: `400 VALIDATION_ERROR`.
- Invalid, expired, or reused state: `401 UNAUTHENTICATED`.
- Google email not verified: `401 UNAUTHENTICATED`.
- Google network, timeout, response, or payload failure: `502 INTEGRATION_ERROR`.
- Unexpected persistence failure: `500 INTERNAL_ERROR`.

Technical causes stay in API logs. Responses and logs must not expose the Google access token, authorization code, PKCE verifier, session token, cookie, or client secret.

Consuming state before contacting Google is intentional. If provider exchange fails, the user must start a new OAuth attempt. This avoids replaying a callback whose outcome is uncertain.

## Testing

Repository/integration coverage:

- Valid state is consumed once and returns its verifier.
- Invalid state returns no authorization.
- Expired state returns no authorization.
- Consumed state cannot be consumed again.
- Two concurrent attempts produce exactly one successful consumption.

Callback integration coverage with mocked Google adapter:

- Valid callback creates OAuth account, local session, cookie, and redirect.
- Existing local user is linked instead of duplicated.
- Existing OAuth account resolves its user.
- Invalid, expired, and reused state create no session or identity data.
- Unverified Google email fails without creating identity data.
- Provider failure returns `INTEGRATION_ERROR`.
- Public response, redirect, database, and captured logs never contain Google tokens or raw session tokens.
